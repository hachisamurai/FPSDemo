# 终端武器库与玩家永久档案

## 目的与规则

终端新增“属性升级 / 武器”页签。武器卡片显示轮廓Icon、名字、解锁状态、每弹丸基础伤害及弹丸数、RPM、基础弹匣容量、装填秒数。未解锁卡片为灰色，但仍能点击查看Tips。选中卡片只打开说明，明确点击“装备为主武器”才会生成或切换主武器。

| 稳定ID | 武器 | 永久解锁条件 | 槽位 |
|---|---|---|---|
| `pistol` | 手枪 | 新档默认解锁 | 固定副武器，按2 |
| `rifle` | 步枪 | 完整通关简单难度十关 | 主武器，按1 |
| `shotgun` | 散弹枪 | 完整通关普通、困难或地狱任一难度十关 | 主武器，按1 |
| `sniper` | 狙击枪 | 完整通关困难或地狱难度十关 | 主武器，按1 |

困难通关即使没有普通记录，也同时满足散弹枪与狙击枪解锁；困难手枪挑战、地狱通关同样满足。步枪仍要求简单通关。通关事实保持真实，不因权限扩展补造普通/简单记录或额外发金币。真正新建存档只生成手枪；同槽死亡或主动放弃后保留已装备主枪、持有库存和死亡时主副槽选择，无需重新去终端装备。通关返回安全区同样保留解锁和当前库存，清空临时属性成长/银币，保留金币永久成长并按基础容量加永久容量补给，新增解锁不直接发枪。已有检查点恢复本槽真实库存，账号最近选择仍只是偏好，不用于跨槽发枪。装备不收费；金币用于安全区属性升级，银币用于关间属性升级，两者不用于装备枪械。

## 困难通关补解锁散弹枪（2026-09-22）

目的：避免玩家直接完成更高难度，却必须重打普通难度才能使用散弹枪。解锁由真实通关事实派生，新增权限本身不产生奖励或额外通关记录，不自动装备武器。

客户端执行链：真实Victory→`RecordVictory`→`Normalize`→`DemoWeaponCatalog::AppendUnlocksForClear`；本地待上传事实与已确认云基线使用同一规则。加载/重载/云合并也执行Normalize，因此有合法历史困难事实的旧档无需再通关即可重算散弹权限。未知事实拒绝；原有档案损坏、保存失败提示和重试方式保持不变。检查点V5、档案SchemaVersion=3、HTTP协议2均不改变，不新增DataTable或uasset。

后端执行链：`WeaponUnlockRules.Resolve`由GET快照和同步事务共用。GET依据`clearedDifficulties`重新派生权限，使旧数据库中仅保存狙击枪的困难投影也能返回散弹枪；GET不写数据库或伪增修订。同步时使用相同权限验证本槽配装/账号偏好，并更新存储投影。请求ID对应的历史缓存回执仍保持幂等，客户端按回执中的真实事实重算权限，后续GET返回新规则。服务端合法hell事实仍需通过原有hard_pistol前置校验，纯武器映射不替代难度解锁验证。

使用：更新客户端并部署对应后端后，已有困难档读取时自动获得权限；玩家在安全区或关间终端的武器页装备。武器卡片显示“普通或更高难度”，困难结算说明同时解锁散弹与狙击。此处修改了后端源码并完成本地构建，未部署正在运行的服务。

影响文件：`Weapons/DemoWeaponCatalog.h/.cpp`、`Player/DemoPlayerProfile.cpp`、`UI/DemoHUD.cpp`、`Tests/DemoSessionTest.cpp`、`Backend/FPSDemo.Api/WeaponUnlockRules.cs`、`Backend/FPSDemo.Api/ProfileService.cs`、`Backend/FPSDemo.RulesTests/`及关联说明。规则入口有调用/拒绝日志；修改映射时同步客户端、后端、展示文案和矩阵，不能只改服务器存储中的派生数组。

验证：`-DemoSessionTest -DemoChallengeTest`从独立新档直接完成困难，断言散弹/狙击解锁、步枪仍锁定、仅一条hard事实以及磁盘重载后保留；继续覆盖困难手枪、地狱和无尽20关。后端用`dotnet run --project Backend/FPSDemo.RulesTests/FPSDemo.RulesTests.csproj`执行实际生产规则的9项矩阵：空集、各难度独立事实、重复/合并事实和未知事实拒绝；该控制台工程直接编译规则文件，无数据库、账号或HTTP依赖。

## 死亡后装备持久化修复（2026-09-21）

目的：装备选择属于同槽长期使用的配装，死亡清空的银币/临时成长不应清空主武器。原日志`FPSDemo.log`在本地20:34:51记录`TERMINAL_EQUIPPED primary=0`，20:49:07死亡进入`ResetActive`，20:49:08新Pawn初始化仅有手枪，玩家20:49:15再次手动装备。根因是旧`ResetActive`创建空库存的新Hub快照，未复制`Weapons/PrimaryId/ActiveSlot`，覆盖了之前终端保存的装备。

执行链：`NotifyPlayerDied → SaveResetCheckpoint → CaptureLoadout(Data,true) → ResetActive → Store`。主动放弃和死亡页返回大厅/退出的保存重试共用该入口。采集当前Pawn的实际武器ID、全部已持有实例及主副槽，生成纯值快照；只将永久MagazineBonus传入补给计算，按每把武器蓝图`MagazineCapacity + 永久容量`补满弹匣，备用弹药恢复`InitialReserve`。死亡旧Pawn自身不会被补血或重新激活。新World仍先创建手枪，再由`RestoreLoadout`验证永久解锁、生成快照中的主枪并恢复活动槽；持手枪死亡也保留主枪，数字1可以切回。

配置与持久化：复用检查点V5既有`Weapons/PrimaryId/ActiveSlot`，无需新配置资产或协议升级；金币、永久成长/价格、弹药类型、无尽纪录继续保留，银币和临时成长继续清空。真实终端装备时立即保存，死亡当帧再保存新的Hub快照，读档/跨World及现有云同步均传递同一组字段。`LastSelectedPrimary`不作为恢复依据，避免同账号另一个存档的选择串入本槽。无活动槽开发World通过`DetachedRestart`传递相同值快照；Editor停止试玩仍删除全部本次临时进度。

边界与失败：新档主槽为空仍合法；仅下载解锁不会自动装备。快照无效或磁盘写入失败保留原槽并显示保存失败，离开死亡页会重试，不把未保存状态当成功。`ResetActive`未传新装备快照时保留原槽装备，不能再次默认为空。新旧Pawn不共享武器Actor或冷却/装填/开镜状态。已被旧逻辑覆盖为空的旧Hub快照没有可信的本槽主枪信息，需在终端重新装备一次，不按账号偏好猜测恢复。

影响文件：`Save/DemoRunSave.h/.cpp`、`Weapons/DemoWeaponComponent.h/.cpp`、`Game/FPSDemoGameMode.h/.cpp`、`Game/DemoSessionFlow.cpp`、`Tests/DemoSessionTest.cpp`、`Tests/DemoArmoryTest.cpp`及关联说明。关键日志为`LOADOUT_CAPTURE`、`RUN_RESET_LOADOUT`、`LOADOUT_RESTORED`，包含稳定主枪ID、活动槽和库存数，便于对照死亡与恢复。参数/函数入口已同步注释和日志。

验证入口：`-DemoSessionTest -DemoEquipmentPersistenceTest`，使用独立本地测试槽，实际通关简单解锁步枪、真实终端购买永久弹匣并装备；GAS伤害致死后重新从磁盘载入、重生、持手枪再次死亡、从死亡页返回大厅读取、V5 JSON往返、主动放弃和新栏位隔离。`-DemoArmoryTest`另覆盖三把主枪库存的无活动槽重开，账号偏好刻意设置为狙击而实际装备为步枪，验证恢复来源正确。使用GAS加速清场，不替代人工平衡验收；实际结果记录在本节后续验证记录中。

本次实际验证：`Saved/Logs/EquipmentPersistenceBuild.log`完成42项Development Editor编译/链接，退出0；`EquipmentPersistenceSessionFinal.log`输出`DEMO_EQUIPMENT_PERSISTENCE_SUCCESS`，逐项覆盖上述活动槽路径，退出0且无Error/Fatal日志；`EquipmentPersistenceArmory.log`输出`DEMO_ARMORY_SUCCESS`，验证完整三难度解锁及无活动槽四把武器库存的死亡恢复，退出0。首次并行回归的Session虽然断言通过，但出现共享AssetRegistry临时缓存写入冲突；最终改为独立运行，已无该错误。Editor日志确认`CLOUD_DISABLED_EDITOR`；JSON往返是本地协议校验，本轮没有启动云服务器或重新做HTTP/Shipping发布测试。既有V5协议未新增字段。

## 设计理念与职责

- `UDemoPlayerProfile` 是自动创建的 GameInstanceSubsystem，拥有跨地图的纯数据档案、读写和上传边界；无需换项目GameInstance类。
- `DemoWeaponCatalog` 用稳定ID连接规则/存档/UI，不把翻译文案、数组顺序或蓝图路径写进协议。当前目录0手枪/1步枪/2散弹/3狙击，组件主型号索引仍为0/1/2。
- `UDemoWeaponComponent` 管当前Pawn库存与装备。初始化缓存四个蓝图类CDO供UI读取真实配置，仅Spawn手枪。主枪首次在终端装备时才Spawn；本局曾持有的主枪保留隐藏实例，切回不会刷新弹药。
- `ADemoPlayerController` 管理页签、Tips及模态输入，HUD只读数据/派发意图；`AFPSDemoGameMode::GetTerminalBlockReason` 共用权威条件，组件内部再次检查。UI禁用不能代替权限检查。
- `ADemoHUD` 沿用Canvas与1280×720设计坐标。Icon优先读取武器蓝图Config中的Texture2D软引用，异步加载后缓存；未配置/加载中/失败时显示四种原生枪械轮廓。卡片属性来自已有蓝图Config/CDO，未硬编码第二套平衡数值。

## 核心执行流程

1. 非Editor游戏的GI启动加载`DemoPlayerProfile`槽；Editor每次试玩创建独立临时槽。新档生成GUID、默认手枪解锁；有效旧档校验版本、GUID、修订、通关ID与时间，从通关凭据重新推导解锁列表。篡改列表本身不会成为解锁来源。
2. Pawn初始化只装备手枪。安全区或关间备战与当前升级终端交互，打开属性页；点击“武器”切页。
3. 任意卡片可弹出说明。Tips期间不注册底层卡片、页签或保存按钮热区，Tab先关Tips，再按Tab关闭终端。武器页数字键不会购买属性，也不会触发武器槽切换。
4. 装备点击重新验证：单人权威、当前Pawn与Controller、存活、Hub/Intermission、正在武器页、真实当前终端存在、距离≤250cm、ID有效且已解锁。装配失败保留旧装备；成功取消射击/装填/瞄准，设置主槽并保存最近选择。
5. 关闭终端后1/2切换本局已经选择的主武器与手枪；空主槽拒绝。旧B输入保留日志兼容入口但不再轮换主武器，HUD改为终端提示。
6. GameMode成功开始战役时生成RunId；第十关完成并进入Victory时记录对应难度凭据，按RunId去重，推进档案修订并保存。重复回调不重复计入。前九关清场、奖励和失败不授予解锁。胜利页显示解锁武器和本地保存状态。返回Hub继续挑战时，先确认旧RunId再生成新RunId，因此第二轮不同难度可独立解锁；旧Victory存档读取也走同一幂等入口。

## 数据结构

定义位于 `Source/FPSDemo/Player/DemoPlayerProfile.h`。二进制外壳 `UDemoProfileSave` 仅包含 `FDemoPlayerProfileData Data`；局内金币、GAS数值、弹药、Actor/类路径、登录令牌均不写入永久档案。

| 字段 | 类型/默认 | 用途和约束 |
|---|---|---|
| SchemaVersion | int32 / 3 | 档案结构版本；未知未来版本保护原文件，禁止降级覆盖；地狱/无尽事实见战役配置说明 |
| ProfileId | GUID字符串 | 本地玩家标识；不是服务器账号凭证 |
| LocalRevision | int32 / 首次保存为1 | 每次内容变更递增，JSON安全整数；达到上限保护并要求版本迁移 |
| SyncedRevision | int32 / 0 | 已确认的本地版本，必须0≤它≤LocalRevision；小于本地版本即待同步 |
| ServerRevision | 字符串 / 空 | 服务端不透明并发控制令牌；离线无值 |
| UpdatedUtc | ISO8601字符串 | 内容修改UTC时间，不能用于服务端判定合法性或覆盖顺序 |
| Clears | FDemoClearRecord数组 / 空 | 每项RunId、DifficultyId、CompletedUtc；只记录完整战役，RunId去重 |
| UnlockedWeaponIds | FName数组 / pistol | 稳定目录ID派生缓存；加载按云端确认难度与待上传Clears共同重建 |
| LastSelectedPrimary | FName / None | 最近成功装备的主枪ID；未解锁/手枪/未知ID会被清除，不自动发枪 |

`FDemoClearRecord` 的 `DifficultyId` 允许 `easy / normal / hard / hard_pistol / hell`；后两项的难度解锁规则见[战役配置与难度](战役配置与难度.md)。V2起Clears作为待上传队列；服务器确认且本地落盘成功后才清理对应记录，完整历史保存在MongoDB的campaign_runs集合。CloudClearedDifficulties保留确认难度基线，RecentAcceptedRuns最多128项防近期重复回调。PreferenceRevision/SyncedPreferenceRevision独立记录武器偏好变更与确认，分批通关确认不会吞掉偏好。V1完整通关记录在加载时迁移为待确认事实。当前一个匿名账号对应一个永久档案，多账号切换UI未实现。

## 本地存档、恢复与失败处理

正式非Editor游戏的标准路径为`Saved/SaveGames/DemoPlayerProfile.sav`，备份`DemoPlayerProfile_Backup.sav`；打包后实际根路径由UE平台SaveGame系统决定，不硬编码工程磁盘路径。平台UserIndex为0。

Editor的PIE/SIE/Standalone每个GI使用`DemoEditorProfile_<PID>_<GUID>`本地临时槽，停止时删除主档和备份、清空解锁/通关；同次运行跨地图和返回大厅保留。强制停止Standalone由父Editor监视器补做清理；不读取正式或云进度。完整流程、边界与实际启停验证见[暂停与检查点存档](暂停设置与检查点存档.md)。

每次内容变更同步保存：先把有效旧主档写入备份，再写新主档。备份失败时不继续覆盖主档，内存仍保留新进度；主档写入失败时同样保留内存和错误提示。下次修改、“保存重试”及正式游戏子系统退出会尝试再次写入，Editor停止则直接清理临时档。此实现有一代备份，不宣称磁盘断电的事务级原子性。

主档损坏或缺失时尝试有效备份；不把损坏主档覆盖到好备份。备份恢复会标记待修复，下一次保存修复主档。主档为未来SchemaVersion时不回退旧备份覆盖它；主备均无效或类型不符时进入只读保护，保留文件，UI明确提示。加载失败的新会话可继续玩，但不能把未保存进度声称已落盘。

`ReloadFromDisk()` 是开发/未来档案管理入口，存在未落盘变更时拒绝，避免老文件覆盖内存新进度。没有新增“清空玩家存档”按钮或自动删除正式存档行为。

## 实际云同步边界

编辑器/PIE/Editor Standalone仅本地存档，不创建HTTP/云同步子系统。以下云流程只在打包游戏启用；编辑器不显示云状态和云操作按钮。

正式联网由UDemoCloudSync调用独立FPSDemoOnline模块，以协议2访问ASP.NET Core后端。永久进度和三个战役检查点都同步，但本地数据仍分开保存。启动认证后优先重放耐久发件箱，再绑定/下载/合并；超时重用同一请求ID，服务器确认并本地落盘后才清理发件箱。

ApplyCloud校验服务器投影，将确认难度和未确认本地记录合并，保留尚未上传的装备偏好。最近主武器始终只是偏好，下载解锁不生成装备。检查点按槽版本检测冲突，大厅提供保留本机/使用云端并先归档两份副本。武器页显示本地保存与云同步状态，“保存重试”同时重试本地落盘与网络连接。

BuildUploadJson/AcknowledgeUpload作为原有离线诊断与回归接口保留，不是生产HTTP提交/确认路径。其protocolVersion=1导出不得发送给新后端；生产同步只能通过请求ID、绑定与账号匹配的协议2回执调用ApplyCloud。

后端接受的单人离线通关标记offline_accepted；认证、幂等、字段校验不等于服务器验证了战斗真实性。实际集合/事务/协议见[MongoDB玩家存档设计](MongoDB玩家存档设计.md)，配置和验证见[云存档运行与验证](云存档运行与验证.md)。
## 使用与配置

- 打开编辑器后从大厅开始，走到升级终端按E，点击“武器”。新档只能查看三把锁定主武器的解锁条件；手枪卡说明固定副槽。
