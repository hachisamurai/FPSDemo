## Visual Studio编译时中文Git路径导致UBT崩溃（2026-09-21）

### 原因与修复

本次用户编译日志在`Using 'git status' to determine working set`后中断；按同一Visual Studio参数重新执行后，`Saved/Logs/VisualStudioBuildReproduce.log`捕获`System.ArgumentException: Path fragment ... contains invalid directory separators`，进程退出码为-532462766。调用栈指向UE5.4的`GitSourceFileWorkingSet.OutputDataReceived → AddPath → FileReference.Combine`，尚未进入项目C++编译。

UBT通过`git status --porcelain`查找工作集。Git默认将中文路径显示为带引号的八进制转义文本，而此版本UBT直接把文本当路径拼接，因转义反斜杠而崩溃。此前命令行验证仅用进程环境临时设置`core.quotepath=false`，没有持久化，因此从Visual Studio启动的构建仍然失败。

在本仓库根目录执行下述设置，让Git保留中文路径，供现有UBT正确解析：

```powershell
git config --local core.quotepath false
git config --show-origin --get core.quotepath
```

本次已写入该仓库`.git/config`，预期查询结果为`.git/config false`；不修改全局Git配置、引擎源码、中文文档文件名或游戏逻辑。该字段仅控制Git路径输出形式，不改变文件内容或编码。该配置不随提交分发，新克隆仓库需单独执行；仅在脚本中设置临时环境变量不足以修复IDE构建。路径中若存在引号、制表符等其他Git强制转义字符，则需另行排查UBT路径解析，不能将本修复视为支持任意特殊文件名。

### 验证与维护

复验使用用户日志中的双目标命令：`FPSDemoEditor Win64 Development`和`ShaderCompileWorker Win64 Development -Quiet`，保留`-WaitMutex -FromMsBuild -architecture=x64`，不设置临时`GIT_CONFIG_*`环境变量。原始UBT日志已保留到`Saved/Logs/VisualStudioBuildOriginal.log`，失败复现和修复后日志分别为`VisualStudioBuildReproduce.log`与`VisualStudioBuildFixed.log`。修复影响仅为本仓库Git配置及本文；不需要运行玩法回归来验证路径输出设置。

实际复验已通过：56项编译/链接/元数据操作完成，构建进程退出0，总耗时31.93秒；日志未出现编译错误或上述异常。当前Visual Studio重新生成应直接使用已持久化的本仓库设置，无需额外命令行环境或重命名文档。

## Windows 运行包资源遗漏（2026-09-20）

### 原因和证据

用户在 Windows Launch On 运行时点击开始，收到 `Missing combat DataTable or incorrect row type; import Content/Data tables`。这是 `DemoCombatConfig::Validate` 对“表为空”和“行类型错”的共用提示；本次日志已经进一步证明是 **Cook/Stage 遗漏资源**，不能仅凭这句提示让用户重新导入或修改表结构。

- `Saved/Logs/FPSDemo.log` 启动记录（UTC 10:31:32）明确报找不到 `/Game/Data/DT_Enemies`、`DT_Difficulties`、`DT_Levels`；UTC 12:12:06 的配置拒绝是稍后点击开始时的结果。
- `Content/Data` 中三张源 `.uasset` 都存在；原 `Saved/Cooked/Windows/FPSDemo/Content`、`Saved/StagedBuilds/Windows/FPSDemo/Content` 及 `Manifest_UFSFiles_Win64.txt` 未收录它们。
- 同一启动还缺少 `/Game/Weapons/Blueprints/BP_Weapon_Rifle` 和 `/Game/Weapons/Input` 的输入资产，并报 `Missing combat InputAction assets`。
- 实际 UAT 命令是 BuildCookRun 的 `-build -cook -map=... -stage -deploy -run`（Launch On）。表及武器由原生默认软路径/运行时 LoadObject 加载；这次按地图收集依赖没有覆盖上述路径。编辑器能从完整 Content 加载，不代表平台 Cook 输出包含它们。

### 修复、设计与维护

在 `Config/DefaultGame.ini` 的 `[/Script/UnrealEd.ProjectPackagingSettings]` 下增加：

```ini
; 三张战役 DataTable 的运行包依赖。
+DirectoriesToAlwaysCook=(Path="/Game/Data")
; 四个武器蓝图、战斗输入 Action/Mapping 的运行包依赖。
+DirectoriesToAlwaysCook=(Path="/Game/Weapons")
```

对应编辑器 Project Settings → Packaging → Additional Asset Directories to Cook。仅显式纳入两个运行目录，不要求全项目 Cook，也不改表数据、GAS 或关卡逻辑。引擎 `UCookOnTheFlyServer::CollectFilesToCook` 读取该配置，将目录内资产及其依赖交给平台 Cook，再由 Stage 收集；其语义也见 [Epic 打包配置文档](https://dev.epicgames.com/documentation/unreal-engine/API/Developer/DeveloperToolSettings/UProjectPackagingSettings)。项目仍不依赖运行时读取 `Config/Combat/*.json`。

修改 `.ini` 后建议保存工作并重启编辑器，让设置面板重新读取配置；重新 Cook 和 Stage/Package，旧部署包不会自动更新。用新的输出目录可避免误启动旧包。不需要重新导入三张源表，也不要把未 Cook 的 `.uasset` 直接复制到旧发布包；打包可能采用 Pak/IoStore，检查时需同时看 Cook 产物、容器和运行日志。

新增运行时软路径目录必须同步此清单；若未来使用 AssetManager/PrimaryAssetLabel，应保持明确的 AlwaysCook 规则并重新验证。未覆盖的目录仍可能发生相同问题；不应为了绕过配置校验而回退硬编码数值。影响文件：`Config/DefaultGame.ini`、`Game/FPSDemoGameMode.h` 的收集说明注释、本文、`战役配置与难度.md`、`武器系统.md`；没有改 C++ 行为，无需为本次配置修复重编引擎。

## 编辑器全解锁命令与包体日志（2026-09-22）

### 使用与生效范围

在单人PIE或Editor Standalone游戏中按`~`打开游戏控制台，输入：

```text
Demo.Debug.UnlockAll
```

不带参数。立即开放手枪、步枪、散弹枪、狙击枪及普通/火焰/冰冻/穿透弹权限；仍通过终端选择装备，不自动发枪、装配弹药、补弹或赠送金币。当前打开的终端下一帧读取新权限；可在大厅或战斗中输入，具体装配仍遵循原终端/安全区规则。重复执行幂等，无需购买特殊弹药。

权限由当前GameInstance的UDemoPlayerProfile持有，跨地图、死亡、返回大厅及本次试玩切换槽仍有效；停止试玩即销毁，新PIE恢复正常解锁规则。不新增通关事实、不解锁地狱/无尽难度、不领取通关奖励、不推进永久档案修订。已装配弹药在后续正常Editor临时检查点中可被捕获，全部临时档仍随停止试玩清空。命令不改变现有WITH_EDITOR禁用云子系统的边界。

控制台注册、回调、GI调试字段和接口、弹药权限分支全部包在`#if WITH_EDITOR`中。Development/Test/Shipping非Editor包都没有命令注册或全解锁接口，不是仅隐藏菜单或依赖运行时开关。命令使用控制台传入的World，不搜索其他PIE实例；无World、非游戏World、非Standalone网络模式或多余参数时拒绝并打印原因。请使用当前试玩的游戏控制台，编辑器普通预览World的控制台不生效。

### 日志策略

`LogFPSDemo`与`LogDemoOnline`按编译目标定义默认级别和编译上限：

| 环境 | 默认级别 | 编译上限 | 行为 |
| --- | --- | --- | --- |
| Editor/PIE/UnrealEditor -game | VeryVerbose | All | 保留函数/接口/回调与高频埋点，可用LogCmds临时降噪 |
| 非Editor Development/Test/Shipping | Display | Display | 裁掉Log/Verbose/VeryVerbose及参数求值；保留Display、Warning、Error、Fatal |

关键成功事件包括战役阶段、关卡开始、检查点成功写入、属性/弹药购买、通关金币及武器解锁、续玩Hub、云确认和退出同步完成。失败原因继续用Warning/Error。不要把逐帧属性读取、每颗弹丸、AI移动、正常轮询或通用函数入口提升为Display。

DefaultEngine.ini不再给项目类别共享强制VeryVerbose。即使包体通过旧用户配置或`-LogCmds="LogFPSDemo VeryVerbose,LogDemoOnline VeryVerbose"`请求详细日志，也不能恢复已裁掉的调用日志。此策略针对项目类别，不全局压制UE引擎/第三方诊断类别。

UE默认关闭Shipping日志；FPSDemo.Target.cs为Shipping显式设置bUseLoggingInShipping=true和Unique构建环境，使关键日志可用且不污染共享UEGame引擎产物。当前工程使用源码引擎，首次Shipping独立构建会重编相关引擎组件；本轮Development包验证不等同于完整Shipping发行验收。不要使用bOverrideBuildEnvironment复用不同宏的引擎二进制，也不要为了恢复Debug命令给包体定义WITH_EDITOR。
